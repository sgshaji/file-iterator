## 1. Requirement

### 1.1 Functional

| # | Requirement |
|---|---|
| R1 | When a template document is published, regenerate every document affected by that template. |
| R2 | Source documents live under one folder of a SharePoint library, at any depth. |
| R3 | Only `.docx`, `.doc` and `.pdf` source documents are in scope. |
| R4 | Folders named `Archive` are never a source. `AD Documents` is not a source — it is the **output** location. |
| R5 | Each document is regenerated by invoking the Copilot Studio agent once, with the source content and the template identity. |
| R6 | Standard SharePoint connector only. No premium connectors, no Entra app registration. |
| R7 | The previous version of every overwritten output must be recoverable. |

### 1.2 Governing constraints

| # | Constraint | Source |
|---|---|---|
| C1 | The library exceeds SharePoint's 5,000-item list view threshold. Recursive enumeration throttles. | Investigation report §4.1 |
| C2 | A single Power Automate action output cannot exceed 16 MB. | Investigation report §4.2 |
| C3 | The SharePoint connector permits 600 calls per connection per minute. | Investigation report §4.3 |
| C4 | Agent invocation is metered. It is the dominant cost of this solution. | Design premise |
| C5 | Bulk regeneration overwrites real business documents. The job is destructive. | Design premise |

## 2. Design Principles

**P1 — The agent call is the only expensive operation.** SharePoint reads, list writes and flow actions are covered by existing licensing. Every design decision is measured against the number of agent invocations it causes.

> **Never invoke the agent for a document that does not need it, and never invoke it twice for the same result.**

**P2 — Separate planning from execution.** Planning is cheap, fast and reversible; it produces a list of intended work and invokes nothing. Execution is expensive and destructive. A human approves the transition between them.

**P3 — State lives in a list, not a variable.** Persisted per-document status makes the job resumable after failure, bounded in run duration, immune to the 16 MB output cap (C2), and observable without run-history archaeology.

**P4 — Enumerate once, maintain incrementally.** The verified folder walk costs hundreds of SharePoint calls (C1). Running it on every template change is waste. It runs once as a backfill; a size-independent created/modified trigger keeps the index current thereafter.

**P5 — Bounded batches, not long runs or blind parallelism.** Throughput is tuned by batch size and schedule interval, both configuration. This is simultaneously the throttle for C3 and C4.

**P6 — Validate before writing; archive before overwriting.** An unvalidated agent response must never reach a business document (C5). A file copy is cheap insurance against a run that has to be undone.

## 3. Architecture

Six flows, three lists. All standard connector.

```
                    TEMPLATE PUBLISHED
                           │
                           ▼
   ┌────────────────────────────────────────────────────────┐
   │ FLOW A — PLAN            (rare · cheap · 0 agent calls) │
   │  1 debounce: Status = Published?                        │
   │  2 fingerprint unchanged?           → exit, no run      │
   │  3 query DocumentIndex for affected documents           │
   │  4 apply cost filters F1 F2 F3                          │
   │  5 cap check → second confirmation if over cap          │
   │  6 create RegenerationRun + RegenerationWorkItem rows   │
   │  7 request approval                                     │
   └────────────────────────────────────────────────────────┘
                           │ approved
                           ▼
   ┌────────────────────────────────────────────────────────┐
   │ FLOW B — PROCESS BATCH   (scheduled · bounded)        ◄─┼──┐
   │  1 claim up to BatchSize Pending items (→ InProgress)   │  │
   │  2 per item:                                            │  │ repeats
   │       read source → invoke agent → VALIDATE →           │  │ until
   │       archive existing output → write new output →      │  │ queue
   │       mark Succeeded / Failed                           │  │ empty
   │  3 backpressure: stop claiming on throttle/capacity     │  │
   │  4 reap stale InProgress items back to Pending          │  │
   └────────────────────────────────────────────────────────┘ ─┘
                           │ queue empty
                           ▼
   ┌────────────────────────────────────────────────────────┐
   │ FLOW C — FINALISE                                       │
   │  close run · summary · alert on failures · retry entry  │
   └────────────────────────────────────────────────────────┘

   ┌────────────────────────────────────────────────────────┐
   │ FLOW D — ROLLBACK        (rare · manual)                │
   │  restore archived version for every item in a run       │
   └────────────────────────────────────────────────────────┘

   ┌────────────────────────────────────────────────────────┐
   │ FLOW E — INDEX BACKFILL  (once · folder walk · chunked) │
   │ FLOW F — INDEX DELTA     (file created/modified)        │
   └────────────────────────────────────────────────────────┘
```

### 3.1 Why the index list exists

Flow A must answer "which documents does this template affect?". Answering it by walking the tree would incur the full enumeration cost (C1) on **every** template change. Instead:

- **Flow E** (split into E1 start + E2 worker) walks the tree once, using the method verified in the investigation report §9 — direct children only, recursion supplied by the flow.
- **Flow F** keeps the index current using the folder-scoped *When a file is created or modified (properties only)* trigger, which is unaffected by library size.
- **Flow A** then answers the question with a single indexed list query.

The expensive enumeration happens once, not once per run.

### 3.2 Why planning and execution are separate flows

A single flow that enumerates, decides and regenerates would: exceed run duration on any realistic tree; lose all work if it failed midway; give no way to inspect intended work before it becomes destructive; and offer no natural throttle. Splitting them addresses all four, and costs only the work queue list.

## 4. Data Model

Three SharePoint lists. Full column definitions in [Configuration Reference](#13-configuration-reference) and in `provisioning/`.

### 4.1 `DocumentIndex` — one row per file in scope

Maintained by Flows E and F. Read by Flow A.

Key: **`UniqueId`** (the SharePoint file GUID), not path. Paths change when folders are renamed; a path key silently produces duplicate rows, which means duplicate agent calls, which means duplicate cost.

| Column | Purpose |
|---|---|
| `UniqueId` | Primary key. SharePoint file GUID. |
| `FileName`, `ServerRelativeUrl`, `ParentFolderUrl` | Location |
| `Extension`, `SizeBytes`, `TimeLastModified`, `Depth` | Selection and diagnostics |
| `DocumentRole` | `Source` \| `Output` \| `Template` \| `Archived` |
| `TemplateName`, `TemplateFingerprint` | For outputs: which template version produced this. **Drives cost filters F1 and F3.** |
| `LastSeenRunId` | Set by every backfill. Rows not seen by a completed backfill are stale. |
| `IsExcluded` | Row retained but never selected as a source |

### 4.2 `RegenerationRun` — one row per regeneration job

| Column | Purpose |
|---|---|
| `RunId` | GUID, generated by Flow A |
| `TemplateName`, `TemplateFingerprint`, `TemplateVersion` | What triggered the run |
| `Status` | `Planned` \| `AwaitingApproval` \| `Approved` \| `Running` \| `Completed` \| `CompletedWithErrors` \| `Cancelled` \| `RolledBack` |
| `PlannedCount`, `SucceededCount`, `FailedCount`, `SkippedCount` | Progress and reporting |
| `AgentCallCount` | **Headline cost metric.** If this approaches `PlannedCount` on every run, the cost filters are not working. |
| `IsDryRun` | Plan-only run, no execution |
| `RequestedBy`, `ApprovedBy`, `StartedAt`, `CompletedAt` | Audit |

### 4.3 `RegenerationWorkItem` — one row per document per run

The work queue. Written by Flow A, claimed and updated by Flow B.

| Column | Purpose |
|---|---|
| `RunId` | Groups items into a run |
| `SourceUniqueId`, `SourceUrl` | The document to regenerate. `SourceUniqueId` is the idempotency key. |
| `TargetUrl` | Where the output is written |
| `ArchiveUrl` | Where the previous output was archived. **Rollback depends on this.** |
| `TemplateName`, `TemplateFingerprint` | Recorded so filter F3 can skip already-current outputs on a re-run |
| `Status` | `Pending` \| `InProgress` \| `Succeeded` \| `Failed` \| `Skipped` |
| `AttemptCount`, `ErrorMessage`, `ValidationResult` | Retry control and diagnosis |
| `ClaimedAt`, `ClaimedBy`, `CompletedAt` | Claim ownership and stale-claim reaping |

**Indexing.** `Status` and `RunId` must be indexed columns — Flow B queries on them every cycle. Completed runs are archived out periodically so the queue does not drift toward the same threshold problem it was built to avoid.

## 5. Flow A — Plan Regeneration Run

**Trigger:** *When a file is created or modified (properties only)*, scoped to the template folder.

Produces work items. **Invokes the agent zero times.**

### 5.1 Debounce — gate 1

The modify trigger fires several times for a single human edit (autosave, metadata stamping, check-in). Regenerating hundreds of documents on a spurious trigger is both expensive and destructive.

The flow therefore does **not** act on any modification. It requires an explicit publish signal: a `Status` column on the template set to `Published` by the author. Anything else terminates immediately.

The template folder and the output folder are **strictly disjoint**, so the flow's own writes can never re-trigger it.

### 5.2 Fingerprint check — gate 2 (cost filter F2)

Not every publish changes the output. Formatting tweaks, metadata edits and re-saves do not warrant regeneration.

Flow A computes a fingerprint of the template's substantive content and compares it with the fingerprint stored on the most recent completed run for that template. **If unchanged, the run is abandoned with zero work items and zero cost.**

This gate alone eliminates the entire spurious-trigger class, which is otherwise the largest single source of wasted spend.

### 5.3 Resolve affected documents (cost filters F1 and F3)

A single indexed query against `DocumentIndex`, then:

| Filter | Rule | Saving |
|---|---|---|
| **F1 — which template** | Only documents whose recorded `TemplateName` matches the changed template. A change to `AD Template.docx` must not regenerate documents built from `HR - Position Description Template.docx`. | Proportional to the number of templates |
| **F2 — material change** | Applied at §5.2 | Eliminates spurious runs entirely |
| **F3 — already current** | Skip any document whose output already records the new `TemplateFingerprint`. | **Makes re-runs after partial failure cost only the outstanding work.** This is what makes the whole job idempotent. |

Documents excluded by R4 (`Archive`, and outputs in `AD Documents`) are never candidates.

### 5.4 Cap check

If the planned count exceeds `MaxDocumentsPerRun`, the run is held at `AwaitingApproval` with an explicit warning and requires a second, deliberate confirmation.

This is the circuit breaker: it stops a wrong template, or a misconfigured filter, from turning into a large bill.

### 5.5 Write and approve

Create the `RegenerationRun` row, write one `RegenerationWorkItem` per planned document, then request approval showing template name, version, planned count and a sample of paths.

**Nothing is written to any business document until a human approves.**

If `DryRun` is set, the flow stops here permanently. The work items exist for inspection and are never executed — this is the free rehearsal described in §14.

## 6. Flow B — Process Regeneration Batch

**Trigger:** recurrence, every `ScheduleIntervalMinutes`.

The only flow that invokes the agent, and the only flow that writes business documents.

### 6.1 Claim

Query `RegenerationWorkItem` for `Status eq 'Pending'` on an approved, running run, ordered oldest first, `top = BatchSize`. Set each to `InProgress` with `ClaimedBy` and `ClaimedAt`.

Claiming before processing prevents two overlapping batches from regenerating the same document twice — which would be both wrong and double the cost.

**Concurrency is off by default.** Parallel invocation multiplies capacity burn rate and makes double-processing possible unless claiming is genuinely atomic. It is an optimisation to add after measurement, not a starting assumption.

### 6.2 Per item

```
1  Read source document      content + any library metadata the agent needs
2  Invoke agent              source content + template identity + output contract
3  VALIDATE response         ── fails ──► mark Failed, leave existing output untouched
4  Archive existing output   copy to Archive/<name>_<yyyyMMdd-HHmmss><ext>
5  Write new output          to AD Documents; stamp template name, fingerprint, run id
6  Mark Succeeded            record ArchiveUrl, CompletedAt
```

**Order is not negotiable.** Validation precedes archiving, and archiving precedes overwriting. Any other order risks either destroying a good document on the strength of a bad response, or overwriting without a recovery point.

### 6.3 Validation (P6)

An agent response is rejected unless all hold:

- non-empty
- plausible size relative to the source (within configured bounds)
- expected sections present
- no truncation marker
- no refusal or apology text pattern

A rejected response marks the item `Failed`, records `ValidationResult`, and **leaves the existing output untouched**. Silent corruption of a business document is a far worse outcome than a visible failure.

### 6.4 Failure isolation and retries

One document's failure must never abort the batch — the per-item scope continues on failure and records the error, so a single malformed source cannot stop 300 others.

Retries are bounded at `MaxAttempts` with backoff, then the item is parked as `Failed` for human review. Unbounded retry on a deterministic failure — a source document that will never generate correctly — is the classic way to exhaust a quota overnight.

### 6.5 Backpressure

On throttling or capacity errors, Flow B **stops claiming** and exits, leaving the remainder for the next cycle. Fail slow, not fast: retrying hard against a capacity limit converts a delay into a cost.

### 6.6 Stale claim reaping

Items left `InProgress` beyond a timeout — the run that claimed them died — are reset to `Pending` at the start of each cycle. Without this, a crashed batch strands its claimed items forever.

### 6.7 Scaling

Run duration is bounded by construction: a queue of 50 and a queue of 5,000 behave identically, the latter simply takes more cycles. Throughput is tuned entirely by `BatchSize` and `ScheduleIntervalMinutes`, both environment variables changeable without redeployment.

If capacity rather than time is the binding constraint, the schedule stretches the run over hours. That costs no more — the same number of agent calls, spread out.

## 7. Flow C — Finalise Regeneration Run

**Trigger:** recurrence.

For any `Running` run with no `Pending` or `InProgress` items: set `Completed` or `CompletedWithErrors`, stamp counts and `CompletedAt`, notify the owner with a summary, and expose a retry entry point that resets `Failed` items to `Pending`.

**The summary reports `AgentCallCount` against `PlannedCount`.** This is the metric that holds the design accountable: if calls approach the full document count on every run, the cost filters are not doing their job, and that — not the flow logic — is where to look.

---

## 8. Flow D — Rollback Regeneration Run

**Trigger:** manual, with a run ID.

Because every overwritten output was archived first and every work item records its `ArchiveUrl`, restoring an entire run is a mechanical pass over the queue rather than a manual scramble. The run is marked `RolledBack`.

Rarely used, but it is the reason the archive step exists. Without it, recovering from a bad run means regenerating everything again — paying a second full run's worth of agent calls on top of the damage.

## 9. Flow E — Index Backfill (folder walk, E1 + E2)

**Trigger:** manual or scheduled reconciliation, off-hours.

Implements the method verified in the investigation report §9, with the improvements identified in review.

Flow E is built as **two flows**, because chunking (I4 below) requires a run to end and a successor to begin:

| Flow | File | Responsibility |
|---|---|---|
| **E1 — Start Index Backfill** | `E1-StartIndexBackfill.json` | Manually triggered. Refuses to start if a walk is already in flight, then seeds the frontier with the root folder and starts E2. Runs once per backfill. |
| **E2 — Index Backfill Worker** | `E2-IndexBackfillWorker.json` | Claims up to `WalkFolderChunkSize` pending frontier rows, enumerates each folder's direct children, upserts index rows, enqueues child folders, then either re-invokes itself or completes the walk. Runs many times per backfill. |

The split is what keeps a walk of any tree size inside the run duration limit: no single run does unbounded work, and a failed chunk resumes from the persisted frontier rather than restarting the walk.

### 9.1 Method

Never ask SharePoint for more than one folder's direct children in a single request. Recursion is supplied by the flow.

The report's §4.1 finding governs: the 5,000-item threshold applies to items SharePoint must **scan**, not items returned. Any recursive-by-path request — native connector, OData `$filter`, or CAML `RecursiveAll` — is a full-library scan in disguise and throttles. A folder's direct children use the folder's internal index and always succeed. Report §6.9 verified this on a folder with 587 immediate subfolders in a 27,000-item library, two minutes after CAML threw `SPQueryThrottledException` on that same folder.

### 9.2 Improvements over report §9

| # | Change | Rationale |
|---|---|---|
| I1 | **One call per folder**, using `?$expand=Folders,Files`, instead of separate `/Files` and `/Folders` calls | Halves call count and throttling exposure (C3). Report §6.7 verified this endpoint at 27k but classified it "building block only" for not being recursive — non-recursive is exactly what the walk wants. |
| I2 | **`GetFolderByServerRelativePath(decodedurl='...')`** instead of `...ByServerRelativeUrl` | The Url variant fails on `#` and `%`. Report raises this only as open question Q5; in an HR library such names are near-certain. Adopted as default rather than discovered during customer testing. |
| I3 | **Frontier persisted in a list**, not an array variable | Makes the walk resumable, observable, and immune to the 16 MB cap (C2). The report's §9.7 names the variable as a known limitation. |
| I4 | **Chunked execution** — process a bounded number of folders per run, then re-queue and exit | No single run approaches the duration limit, whatever the tree size. |
| I5 | **Exclusions applied before enqueueing** | Retained from report §9.4. An excluded subtree of any size costs nothing. |

Exclusions are held in an environment variable, not hardcoded in a condition, so the customer can change them without editing the flow.

### 9.3 Deletions

Each row is stamped with `LastSeenRunId`. Rows not seen by a **completed** backfill are marked stale rather than hard-deleted. Neither a walk nor a modify trigger detects deletions on its own.

## 10. Flow F — Index Delta

**Trigger:** *When a file is created or modified (properties only)*, folder-scoped.

Upserts a single `DocumentIndex` row. Unaffected by library size, so it holds regardless of how large the library grows.

This is what makes P4 work: the walk runs rarely, the trigger keeps the index current, and Flow A always reads a fresh index at negligible cost.

## 11. Cost Model

| Cost | Driver | Control |
|---|---|---|
| **Agent invocations** | documents × runs | Filters F1/F2/F3; `MaxDocumentsPerRun`; validate-before-write; bounded retries; dry run first |
| SharePoint API calls | folders + documents | Index once (E1/E2), event-driven after (F); batch pacing |
| Flow runs | batch count | `BatchSize` vs `ScheduleIntervalMinutes` |
| Storage | archived versions | Retention policy on the archive folder |
| Licensing | — | Standard connector only, by design (R6) |

**Headline metric: `AgentCallCount` per run**, reported by Flow C.

## 12. Failure Modes and Controls

| # | Failure | Control |
|---|---|---|
| F-01 | Spurious template trigger causes a full regeneration | Publish gate (§5.1) + fingerprint gate (§5.2) |
| F-02 | Wrong template published; hundreds of documents corrupted | Approval gate (§5.5), `MaxDocumentsPerRun` (§5.4), archive-then-overwrite (§6.2), Flow D |
| F-03 | Agent returns refusal or truncated content; written to a business document | Validation before write (§6.3) |
| F-04 | One bad document aborts the whole batch | Per-item failure isolation (§6.4) |
| F-05 | Deterministic failure retried forever, exhausting quota | `MaxAttempts` + park (§6.4) |
| F-06 | Batch dies mid-run; work lost or items stranded | Persisted queue (P3) + stale claim reaping (§6.6) |
| F-07 | Same document regenerated twice; double cost | Claim before process (§6.1); `SourceUniqueId` key (§4.1); filter F3 |
| F-08 | Enumeration throttles on the over-threshold library | Direct-children folder walk (§9.1) |
| F-09 | Accumulated results exceed the 16 MB action cap | Per-folder and per-item writes to lists (P3, I3) |
| F-10 | Connector rate limit hit during a long walk or batch | Batch pacing, backpressure (§6.5) |
| F-11 | Folder names containing `#`/`%` break enumeration | `GetFolderByServerRelativePath` (I2) |
| F-12 | Output flow re-triggers the plan flow | Template and output folders strictly disjoint (§5.1) |
| F-13 | Work queue itself grows past the threshold | `Status`/`RunId` indexed; completed runs archived (§4.3) |
| F-14 | "Empty, no error" mistaken for success | Flows fail loudly with a typed error; report §13 lesson 3 |

## 14. Build and Validation Order

Deliberately ordered so that everything cheap and reversible is proven before anything expensive or destructive runs.

| # | Step | Agent cost | Proves |
|---|---|---|---|
| 1 | Import solution; provision the three lists; set environment variables | none | Configuration is correct |
| 2 | Run the Flow E1/E2 backfill on the test tree (`001NH`) | none | Enumeration works end-to-end. **The investigation report §9.6 records that the assembled loop has never been executed as a complete flow — this is the first thing to make green.** |
| 3 | Enable Flow F; modify a file; confirm the index updates | none | Incremental maintenance works |
| 4 | Run Flow A with `DryRun` on | none | Affected-document resolution and the cost filters produce the expected count **before anything is spent** |
| 5 | Approve a 5-document pilot; run Flow B | 5 calls | Agent output quality, and measured call latency |
| 6 | Measure worst-case latency; set `BatchSize` and `ScheduleIntervalMinutes` | none | Throughput sized from data, not guesswork |
| 7 | Test Flow D rollback on the pilot | none | Recovery path works before it is needed |
| 8 | Unlock full runs | metered | — |

Steps 1–4 cost nothing in agent capacity and de-risk the expensive part. Validating output quality on 5 documents before committing to hundreds is the highest-return control in the design.

**Latency measurement (step 6)** must use the same invocation path the flow uses, not the Copilot Studio test pane, across a short, typical and largest document, three times each, at normal load. Size the batch from the **worst case**, not the average: one slow document stalls a sequential loop. If worst-case latency approaches the action request timeout, synchronous invocation is unsafe and Flow B must move to an asynchronous handoff — the agent writes its result to staging and updates the work item; a separate pass validates and writes. The persisted queue already supports this; it is why state is in a list.

## 15. Open Questions

| # | Question | Impact |
|---|---|---|
| Q1 | Worst-case agent call latency, and the tenant's capacity limit | Sets `BatchSize` and `ScheduleIntervalMinutes`; may force the asynchronous variant of Flow B (§14) |
| Q2 | Does a template change invalidate every document, or only those built from that template version? | Sets the size of every run — filter F1 |
| Q3 | How many source documents are in scope, and how deep is the tree? | Sizes the whole solution. Still open question Q4 in the investigation report. **If the true scope is a few dozen rarely-changing documents, this design is over-engineered and a single approved flow with a loop is the right answer.** |
| Q4 | Is overwrite-in-place acceptable, or must outputs be versioned? | SharePoint versioning on the output library may make the explicit archive step redundant |
| Q5 | Who approves a run, and what is the acceptable blast radius of a bad template? | Sets `MaxDocumentsPerRun` and the approval routing |
| Q6 | Do multiple templates map to different document types? | If so, the index needs a template-to-source mapping rather than a single global template |
| Q7 | Are there folders with `#`, `%` or parentheses in the customer tree? | Mitigated by I2, but worth confirming |

## 16. Trade-off

This is more moving parts than a single flow. It is justified **only** because the work is expensive (C4) and destructive (C5): hundreds of metered agent calls overwriting real business documents.

If Q3 reveals a small, stable document set, the proportionate answer is a single approved flow with a loop, and this design should be reduced accordingly. The architecture is sized off that number, and it remains unanswered.
