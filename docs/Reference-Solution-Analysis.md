# Reference Solution Analysis

What `reference-solution/pdconversionassistant_1_1_0_1.zip` actually contains, and
what the harness had to do differently.

This is a record of evidence, not opinion. Every claim below is traceable to a
file inside the export. Where I got something wrong earlier, that is recorded too
(see [P7, withdrawn](#p7-withdrawn)) — a defect list is only useful if its
mistakes are visible.

The export is **read-only**. Everything here was produced by extracting a copy to
a temporary directory. `scripts/check_reference_untouched.py` enforces that in CI.

## 2. The finding that shapes everything: the agent is not in this solution

`solution.xml` declares exactly **one** root component:

```xml
<RootComponent type="29" id="{6e2ce50c-f215-a123-7030-4c300c97aa04}" behavior="0" />
```

Type 29 is a workflow. There is no bot root component, and `customizations.xml`
has no `<bots>` element at all. The agent's own prefix is `cree1_`, which is not
the solution's `cr50b`.

**The agent is an environment resource that the flow consumes.** It is not owned
by this solution; the bot files ship only as dependency payload.

That single fact settles the biggest design question. The harness ships the flow
and *references* the agent — it does not carry, copy or recreate it. Taking
ownership would fork the agent's instructions, its five tools and the
`pd-ad-conversion` skill, and the two copies would drift.

`scripts/validate_harness.py` asserts the harness never declares a `cree1_*`
component, a type-10056 root component, or a `<bots>` element.

Because the invocation mechanism is taken from a working export rather than
inferred, it is the one part of the harness flow I have high confidence in.

## 4. The reference flow

```
Trigger: GetOnUpdatedFileItems  (Template folder, 1-minute recurrence, splitOn)
  → Get files (properties only)   [viewScopeOption: RecursiveAll, $filter, paginationPolicy 5000]
  → Send an HTTP request to SharePoint   [CAML Scope='RecursiveAll']
  → Loop (Foreach, concurrency 1)
       ├── If_Else   "actions": {}   and   "else": {"actions": {}}
       └── Agent     "runAfter": {}
  → Terminate: Succeeded   (unconditional)
```

Read that `Loop` body carefully. `If_Else` has **two empty branches**, and `Agent`
is its **sibling**, not its child, with an empty `runAfter`. The exclusion filter
is fully visible in the designer and has no effect whatsoever. The agent is
invoked for every item, unconditionally.

This is the class of defect that motivated generating the harness flow from code
and checking it mechanically: it is nearly invisible in the designer and obvious
to a parser.

## 5. Defects

Confirmed present in both the 49,947-byte and 89,181-byte exports — the flow did
not change when the skill was added.

### P1 — the exclusion gate is dead
Both branches empty; `Agent` is a sibling. The condition is *also* type-broken
independently: `equals["@toLower(string(contains(...)))", false]` compares the
string `"false"` against the boolean `false`, which is never true. Two independent
bugs in one construct.
→ Guarded by `check_no_empty_branches`.

### P2 — the output folder is inside the input folder
`AD Documents/` sits within `Positions/`, so recursive enumeration re-ingests the
agent's own prior outputs as new input.
→ Harness excludes `Archive` and `AD Documents` **before descending**, so an
excluded subtree costs nothing.

### P3 — enumeration method already proven to fail here
`RecursiveAll` on the connector plus CAML `Scope='RecursiveAll'`. The 5,000-item
threshold counts items **scanned**, not returned, so both are full-library scans.
The investigation report records `SPQueryThrottledException` from exactly this
pattern against the production library.
→ Harness walks direct children only.

### P4 — the CAML action is dead code
Its output is never referenced by any downstream action. It is expensive, it
throttles, and nothing reads it.

### P5 — the agent's response is discarded
Nothing parses the reply; the flow always terminates `Succeeded`. It cannot
distinguish 400 conversions from 400 failures.

This is the most consequential defect, because the agent's own instructions say a
conversion reported complete when it is not is worse than one reported failed —
and the flow around it did precisely that. The skill returns a structured report
*specifically* so a flow can branch on it, and no consumer existed.

### P6 — trigger design guarantees repeated full-cost fan-out
1-minute recurrence on template changes, with `splitOn`. Touching three templates
produces three runs, each fanning across every position, at full agent cost. No
idempotency, no cap, no way to intervene.

### P7 — withdrawn
I originally flagged `templatePath` using `{Path}` (a folder) while `sourcePath`
uses `{FullPath}` (a file) as an inconsistency. **It is correct.** `SKILL.md`
states a folder path means every `.docx` in it, and that a template folder is the
normal case. The reference flow is right and my reading was wrong. Recorded rather
than quietly deleted.

### P8 — every environment value hard-coded
`https://m365cpi10857483.sharepoint.com/sites/DemoFiles`, library GUID
`7e12fd88-03ad-48ad-8b99-6f1c9fb7bd1d`, `/Shared Documents/NH/Template`,
`/Shared Documents/NH/Positions`, and `/sites/DemoFiles` inside the prompt text.
Zero environment variables; connection instances named literally.
→ Guarded by `check_no_hardcoded_environment`.

### P12 — pagination will breach the action output cap
`paginationPolicy.minimumItemCount: 5000`. Property rows run ~8.2 KB, so the 16 MB
per-action output limit is reached near 2,000 rows.

## 6. The most important observation

**The reference flow has never been pointed at the real target.**

Every path in it belongs to the `m365cpi10857483` demo tenant. The production
target — `nhorgau.sharepoint.com/sites/pc`, library `wfpp`, folder
`PD-AD Library/Position Descriptions` — appears nowhere. And its single
enumeration method is the one the investigation report already recorded failing
against that library.

So it is not a working solution needing a scale fix. It is a demo that works at
demo size, and the enumeration problem is guaranteed rather than merely likely.

## 7. The skill contract

`pd-ad-conversion` (`kind: InlineAgentSkill`) ships `SKILL.md` and `pd_tools.py`.
It is a genuine machine contract, and the harness is written against it.

**Scope** — *"One source PD per invocation. Do not scan folders, discover work,
decide what to convert next, or process a library in bulk — that is the flow's
job."* The division of labour is stated explicitly; the harness respects it.

**Output** — one JSON object, no prose, no code fence. `status` is `OK`,
`FAILED` or `SKIPPED`, where `SKIPPED` is used **only** for
`another-format-preferred`. `pd_tools.py` is blunt about why every other empty run
is `FAILED`: reporting a failure as skipped *"hides it from whoever counts how many
documents were actually produced."*

`reason` is a closed set of twelve codes, because *"the workflow branches on this
value, so it cannot be free text."*

**Constants** (`pd_tools.py` lines 70–81) that the flow must agree with:

```python
ARCHIVE_FOLDER_NAME = "Archive"
AD_FOLDER_NAME      = "AD Documents"
OUTPUT_FOLDERS      = (ARCHIVE_FOLDER_NAME, AD_FOLDER_NAME)
CONVERTIBLE_EXT     = (".pdf", ".docx")
```

`check_contract_constants` asserts the harness's environment-variable defaults
equal these. Drift means the flow enqueues work the skill silently declines —
*after* the metered call is spent.

### The skill forced a correction to my own design

`pd_tools.py`'s `sources` command groups files by stem and, for a `Role.pdf` /
`Role.docx` pair, converts one and reports the other as
`SKIPPED / another-format-preferred`.

My plan had the harness iterate **files**. That would invoke the agent twice per
position and pay for a guaranteed skip every time. The harness therefore iterates
**position folders**, matching the skill's own unit of work.

---

## 8. Resolved format boundary

The investigation's original enumeration scope included `.doc`, but the deployed
agent's `CONVERTIBLE_EXT` is `.pdf` and `.docx` only. The implementation therefore
defines automated regeneration scope as `.pdf`/`.docx` and requires legacy `.doc`
files to be migrated before indexing. This is deliberate: queueing `.doc` would
spend a metered call only for the agent to reject it. Adding `.doc` later requires
an independently verified conversion path and a corresponding agent-contract
change; it is not represented as supported until then.

## 9. Reference vs harness

| | Reference flow | Harness |
|---|---|---|
| Trigger | File change, 1-min, `splitOn` | Explicit invocation, typed inputs |
| Enumeration | `RecursiveAll` + CAML | Direct children, breadth-first |
| Exclusions | Present but dead (P1) | Applied before descending |
| Unit of work | Every file | Position folder |
| Agent | Same agent, same connector, same operation | Same agent, same connector, same operation |
| Response | Discarded | Parsed; branches on `OK`/`SKIPPED`/`FAILED`/unparseable |
| Terminal status | Always `Succeeded` | Derived from outcomes |
| Cost control | None | `dryRun` gate + `maxDocuments` cap |
| Configuration | Hard-coded literals | 12 environment variables |
| Verification | None | Generator + validator + CI |

The agent row is deliberately unchanged. **What the agent does was never the
problem.** Everything around it was.
